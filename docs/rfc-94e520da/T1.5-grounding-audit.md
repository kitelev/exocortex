## Methodology

`scripts/audit-starter-kit-groundings.mjs` walks `exocortex-starter-kit/exocmd/**/*.md`, extracts the two grounding properties via regex, joins against the static `KNOWN_REAL_SERVICE_IDS` / `KNOWN_STUB_SERVICE_IDS` sets mirrored from `CliServiceRegistryPopulator.ts`, and emits the JSON fixture committed at `docs/rfc-94e520da/starter-kit-grounding-status.json`. The fixture is the canonical input for the Phase 6 BDD scaffold (`expected.json` per scenario derives from the per-grounding row).

Re-run on every starter-kit change:

```bash
node scripts/audit-starter-kit-groundings.mjs \
  --starter-kit ../exocortex-starter-kit \
  --out docs/rfc-94e520da/starter-kit-grounding-status.json
```

Drift gate (Phase 6 prep): if the audit script ever finds a service id that is neither `REAL` nor `STUB` nor in the `KNOWN_UNREGISTERED` allowlist, it exits non-zero — that's the moment to either port the service or document the gap explicitly.
